The key point

Replit says:

"This is different because it doesn't use the OAuth install flow."

That is only true if the Client ID and Client Secret already belong to a valid installed OAuth app.

The question is:

Where does the client_secret come from?

It comes from the OAuth app you created in the BigCommerce Developer Portal.

And earlier, your implementation already attempted:

Customer Login JWT
    ↓
loginWithCustomerLoginJwt
    ↓
customerAccessToken

and it failed with:

"Invalid login. Please attempt to log in again."

That wasn't a callback failure—it was BigCommerce rejecting the JWT.

At the time, Replit believed it was because the app wasn't installed.

So is this actually different?

Not really.

There are only two possibilities:

Case 1 — Customer Login JWT requires the app to be installed

Then you're back to the original blocker:

OAuth app won't install.
JWT flow can never work.
Case 2 — Customer Login JWT does NOT require the app to be installed

Then Replit should be able to prove that by calling loginWithCustomerLoginJwt directly using your existing Client ID/Secret.

If BigCommerce returns a valid customerAccessToken, great.

If it returns the same "Invalid login" again, you've learned that installation (or some other app state) is still required.
