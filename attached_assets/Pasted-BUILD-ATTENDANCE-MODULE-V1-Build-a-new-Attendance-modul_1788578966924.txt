6. DRIVING TO FIRST STOP FLOW
==================================================

When the employee selects:

Driving to first stop

DO NOT display a manual Time In button.

The employee should not need to interact with the phone while driving.

Immediately begin driving validation.

Display a minimal screen:

Validating...

Please keep your phone safely stored while driving.

The system should determine whether driving can be reliably validated using the capabilities available in the current SalesCore environment.

Do NOT fake driving detection.

Do NOT allow the employee to simply press a button claiming they are driving.

Use the strongest reliable device/browser location and movement signals available in the existing application environment.

If the current web/PWA environment cannot reliably detect driving in the background, do not create an unsafe manual override. Build the driving validation behind a provider/service abstraction and clearly document the platform limitation.

When driving is successfully validated:

Automatically create the attendance record.

No manual confirmation button.

Immediately show:

You're clocked in

[Time]

Started while driving to your first stop.

Then show a brief safety message such as:

Drive safely.
Your attendance has been recorded.
No further action is required.

After the confirmation, transition automatically to the normal active Attendance screen.

10. HOURLY LOCATION CHECKPOINTS
==================================================

While an employee has an active attendance session, collect a location checkpoint approximately every hour.

Do NOT continuously store GPS coordinates.

Create a child table related to the attendance session.

Suggested:

attendance_location_checkpoints

1. id
2. attendance_id
3. captured_at
4. latitude
5. longitude
6. accuracy
7. checkpoint_type
8. capture_status
9. created_at

checkpoint_type can include:

hourly
time_in
time_out
validation

For hourly checkpoints:

Attempt to capture approximately every hour while attendance is active.

The system must account for browser/PWA limitations.

Do not assume that an hourly background location callback will always execute.

If a checkpoint cannot be collected, record the failed/missed checkpoint appropriately rather than fabricating a location.

Do not continuously retry in a way that drains the employee's battery.

The employee does not need to see hourly checkpoint notifications.

11. FIRST FOUR HOUR VALIDATION
==================================================

Implement the previously defined administrative validation.

If an employee starts their day using:

Driving to first stop

the system should silently evaluate their location during the first four hours after Time In.

If the location checkpoints indicate significant warehouse presence during the first four hours, create an Attendance Exception.

This validation must NOT:
1. Change the employee's Time In
2. Automatically change the attendance method
3. Notify the employee
4. Interrupt the employee
5. Display a warning to the employee

It is an Admin/Manager validation only.

The validation should be based on configurable rules rather than hardcoded assumptions.

For example:

First four hour validation window:
4 hours

Warehouse presence review threshold:
60 minutes

These should be configurable in Attendance Settings.

The system should preserve the underlying evidence.

Example:

Driving start:
7:52 AM

Warehouse presence detected:
8:31 AM to 11:42 AM

Warehouse presence:
3h 11m

Create:

Attendance Exception
Driving Start + Warehouse Presence

Status:
Open

Do not label this as misconduct.

It is simply an attendance validation requiring administrative review.
