Apply these changes incrementally without breaking existing functionality. Do not remove or rewrite existing working features unless necessary. Ensure full backward compatibility with current pricing, cart, and checkout behavior.

---

Implement Price Tier Configuration System, Pricing Source Logic, POS UI Badges, and Multi-Layer Pricing Cache Optimization.

---

1. Price Tier Configuration (Settings Page)

Create a settings section to manage up to 10 price tiers.

Each tier must include:
- Tier Label (string) → used for POS badge display
- Customer Group ID (number)
- Price List ID (number)
- Color (hex)
- Enabled toggle (boolean)

---

2. Global Price Tier Controls

2.1 Enable Price Tier System (default OFF)
- When OFF → ignore all price tier logic

2.2 Price Tier Scope Mode

A. Use Only App-Defined Tiers (DEFAULT)
- Only use configured tiers

B. Allow All BigCommerce Price Lists
- Use BC price lists even if not configured
- Use fallback label: "TIER" if not mapped

---

3. Price Tier Matching Logic

When customer is selected:
- Get customer_group_id
- Find matching enabled tier

If found:
- Use mapped price_list_id and label

If NOT found:
- Mode A → ignore tier
- Mode B → allow BC fallback

---

4. Price Tier Pricing Logic

When resolving price:

If tier system enabled:
- Attempt to fetch price list record using:
  - variant_id OR SKU

If record exists:
- Use tier price

If no record:
- fallback to sale_price or default

---

5. Sale Price Edge Case

- If product-level sale_price exists and variant sale_price = 0:
  → Apply product-level sale_price to all variants
- If variant sale_price > 0:
  → Use variant-level sale_price

---

6. Pricing Source System (FINAL LOGIC)

Determine AFTER final price resolution:

Priority:
1. CUSTOM (manual override)
2. HISTORICAL (Last $)
3. PRICE TIER (ONLY if record exists AND used)
4. SALE (if sale_price used)
5. DEFAULT

---

7. Price Source Metadata

Attach to each cart item:

price_source:
- "custom"
- "historical"
- "price_list"
- "sale"
- "default"

---

8. POS UI Badges

Customer Badge:
- Show only if tier is matched AND used

Product Badge:
- Show ONE badge per item

Badge priority:
CUSTOM > HISTORICAL > PRICE TIER > SALE > DEFAULT

Variant Popup:
- Each variant displays its own badge

DO NOT show tier badge if fallback pricing is used

---

9. Price History Rules

- Use tax-exclusive price ONLY
- Do NOT use tax-inclusive values

Stop scanning once required results (e.g. 5) are found

---

10. Multi-Layer Pricing Cache System

3 layers:
1. Local Cache (IndexedDB)
2. Postgres
3. BigCommerce API

---

10.1 Lookup Flow

1. Check Local Cache
2. Else check Postgres
3. Else call API

On success:
- Save to Postgres
- Save to Local Cache

---

10.2 Cache Key Requirements

Cache keys must include:
- customer_id
- product_id
- variant_id (if applicable)
- price_list_id (if tier used)

---

10.3 Local Cache

Store:
- price history
- price list lookups
- recent products

Keep dataset limited  
Optional TTL

---

10.4 Postgres

Store:
price_history:
- customer_id
- product_id
- variant_id
- price (tax-exclusive)
- order_id
- created_at

Prevent duplicates:
(customer_id, product_id, order_id)

---

11. Performance Rules

- Avoid API calls per scan
- Use caching aggressively
- Stop processing early once enough results found
- All pricing operations must be async and non-blocking

---

12. Safety Fallback

If ANY pricing logic fails:
- Fallback to default pricing
- Do NOT break cart or checkout

---

13. Maintain Existing Features

DO NOT break:
- price history dropdown
- Last $ button
- discount controls
- draft orders
- checkout flow

---

Output:

- Fully configurable price tier system
- Accurate pricing source detection
- Correct badge rendering
- Fast pricing lookup via caching
- Safe fallback behavior
- Scalable pricing architecture
