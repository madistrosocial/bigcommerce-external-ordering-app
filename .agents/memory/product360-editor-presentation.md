---
name: Product 360 editor presentation
description: User-approved organization and photo/category interactions for Product 360 catalog details.
---

In Product 360 product details, use the module name “Products” as the page heading; the product name is already shown in the detail card. The Products workspace should use the full available width, with compact fixed table columns, single-line headers, and product/brand names wrapping fully rather than truncating. Keep pricing and cost visually separate from physical specifications. Show assigned categories in a searchable, expandable checkbox tree rather than a flat checklist. Product creation should use the same tree inside a popup selector and use the full available window width. Its Brand field should accept existing or typed names and create a missing BigCommerce brand during product sync. The photo gallery spans the full Details width with 150px tiles, compact editable captions, and an admin option to set the BigCommerce primary image. In the Products table, admins may drop a photo onto a product thumbnail only when the product has no primary image; verify this against BigCommerce before uploading and set the dropped photo as primary. Below the gallery, keep catalog details, pricing, and specifications in the left 70% and categories in a right 30% sidebar. In Variants, show each variant's thumbnail in the first column and let admins upload a missing image directly to that variant.

**Why:** The user explicitly requested and approved these presentation and interaction choices while refining the Product 360 workspace. A primary image affects the catalog thumbnail, so a drop must never overwrite an existing primary; BigCommerce also has a separate variant-image endpoint.

**How to apply:** Preserve these patterns when extending or restyling Product 360. Keep the create form free of a max-width cap, keep variant uploads scoped to the selected BigCommerce variant, and enforce the no-primary condition server-side for dropped product photos.
